# 架构说明

## 组件边界

- **Server**：配置管理 API、节点认证、HTTP 入口和请求路由。
- **Agent**：主动连接公网 Server，并代表指定内网节点访问目标服务。
- **Frontend**：通过 HTTP API 管理服务与节点。
- **SQLite**：存储服务配置和平台元数据。

TunnelHub 不安装、配置、启停或升级 Caddy、FRP。用户可以自行在 Server 前部署 TLS 终止代理，也可以让 Server 直接监听 HTTPS（后续实现）。

## 请求链路目标

1. 客户端访问统一公网入口中的服务域名。
2. Server 根据 Host 匹配启用的服务配置。
3. Server 将请求经已认证的 Agent 隧道发送到对应节点。
4. Agent 访问节点允许范围内的目标地址，并通过隧道返回响应。

当前代码已实现服务配置 CRUD，以及 Agent WebSocket 连接的共享令牌校验、hello/welcome 握手、心跳应答和客户端指数退避重连。服务端使用 `TUNNELHUB_AGENT_TOKEN` 作为开发阶段共享凭证（至少 24 个字符）。此机制不是逐节点凭证系统，也尚未持久化节点在线状态。动态 HTTP 请求转发、按 Host 路由和 WebSocket/SSE 上游转发仍未实现。

## 安全边界

- 当前 Agent 接入使用服务端与 Agent 共享的开发令牌；后续应升级为逐节点凭证、可撤销令牌和权限范围，不能仅凭节点名称加入平台。
- 每个 Agent 应有明确的目标地址访问范围，防止被利用为内网扫描或 SSRF 代理。
- 管理 API 在公网部署前必须增加管理员认证和 CSRF/来源保护。
- 不能把 URL 中携带的用户名、密码存入服务配置。
- 不应将尚未实现认证的管理 API 直接暴露到不可信网络。
